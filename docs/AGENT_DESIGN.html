MockFlow-AI agent design — Flow

Current as of 2026-10-06. This replaces the earlier design document, which described a tool-driven agent (transition_stage, ask_question, assess_response, queued transition acknowledgements, JSON transcript files, one shared worker). None of that is in the code any more. The authoritative contract, with signatures, is RUNTIME_CONTRACT §0; why the tool loop was removed is in AGENT_AUDIT_2026-09.

What Flow is

Flow is the voice interviewer. One interview is one LiveKit room and one agent_worker.py subprocess (spawned by worker_manager.py with the user's own keys, or the owner's keys on the free tier). The voice pipeline is Deepgram STT → an OpenAI LLM → OpenAI TTS, with Silero VAD and endpointing between 0.8 s and 4.0 s.

The interview's shape — which stage it is in, when it moves on, what to ask next — is decided in code. The model's only job is to say the one thing code tells it to say, in natural words. There are no function tools in the speech path, and the session is built with max_tool_steps=1 as a backstop.

Module Role
agent_worker.py Room lifecycle: connect, build the session, finalize and save at the end
interview_runtime.py InterviewAgent, prepare_turn, advance_to, the stage timer, data-channel commands, coding evaluation
interview_turn.py Pure turn logic: should_advance, choose_move, the [FLOW MOVE] note, the closing line, the assessment call
interview_coverage.py TurnAssessment and CoverageLedger — what the candidate has demonstrated so far

How a turn works

When the candidate stops speaking, InterviewAgent.prepare_turn runs (from the SDK's on_user_turn_completed hook on the audio path; directly from the harness in tests):

  1. Assess. One structured call reads the answer: for each signal the current stage needs, absent / partial / demonstrated with a verbatim quote; the four STAR elements where they apply; whether the question was answered; terse / normal / rambling; whether the candidate asked something (repeat, process, feedback, company); whether they said they don't know. The call is started early from STT interim transcripts while the candidate is still talking and has a 2.5 s budget. If it misses, the turn proceeds on the existing ledger and the late result is merged on the next turn.
  2. Ledger. The assessment merges into state.ledger, keyed by the same signal names the final verdict grades with (evaluator.SIGNAL_LIBRARY). Merging only ever raises a level, and credit is cross-stage: a full STAR story told during the introduction counts toward the behavioral questions.
  3. Progress. should_advance moves on when the stage's required signals are covered (after a minimum of two turns in the stage), when the stage is over time, after two empty reads from a terse candidate, or at the depth's turn cap.
  4. Move. choose_move picks exactly one next move: an honest fixed preface for meta-questions, one scaffold for "I don't know", a pin to the result for a rambler, a narrow question for a terse answer, the bank's own follow-up probe for a missing STAR element, otherwise the bank's next question.
  5. Note. One [FLOW MOVE — instructions, not speech] message is added to this turn's chat context. The model's reply to it is the transition; there is no separate acknowledgement turn.

prepare_turn never raises anything but StopResponse (the SDK swallows other exceptions and skips the reply, which is a silent turn). On any internal failure it leaves a short safe note instead.

Stage changes

advance_to() is the only way the stage changes — whether from the turn loop, the Skip button, or the timer. It updates state and the model's instructions, emits one stage_change event to the browser, pushes the next coding problem when entering one, and never speaks.

  • Greeting. One fixed line per track, spoken by code on entry, never generated. The stage walkthrough is shown in the pre-join panel instead. Interviews start in self_intro.
  • Skip. The browser sends skip_stage; Flow advances and immediately asks the new stage's first question.
  • Timer. stage_fallback_timer checks every few seconds. When a stage exceeds its limit it forces the advance and parks the new stage's opening question as pending_move, so it lands as the reply to whatever the candidate says next; if they stay silent for about six seconds, Flow asks it. A coding problem that runs out of time is marked timed out, Flow says so, and the next problem is pushed.
  • Closing. One utterance built by code quotes the candidate's strongest specific evidence and ends with a fixed sentinel sentence. The room is finalized on that sentinel and nothing else; after it Flow stays quiet. If the closing stage runs 60 s without it, the closing line is spoken by the timer.

Coding track

  • Problems come from the vetted bank (coding/problem_bank.py): each has an entrypoint, Python starter code, hidden test cases and a reference solution, and CI proves every reference solution passes its own tests. Difficulty follows level (junior → easy, mid → medium, senior and above → hard); a short pool steps down one level at a time.
  • What the browser gets is a client-safe view: title, description, examples, constraints, hints, entrypoint, starter code, time limit. The test cases and reference solution never leave the server, and the saved interview row stores the same safe view.
  • Submissions reach the agent only when the candidate presses Submit. One evaluation path (_evaluate_code_async): when PISTON_ENABLED is on and the language is Python, the code runs against the hidden tests and the pass count decides correctness; the model grades approach, complexity and edge cases and writes the spoken feedback. When execution is off or fails, the result is labelled not executed, with the reason. Evaluator outages retry with backoff and end in an explicit evaluation_error, never a stuck editor.
  • Progress is decided in code: a pass or the third attempt ends a problem; the interview cannot close with a problem still open.
  • Persistence. Each submission (code, attempt, evaluation, execution provenance) is recorded in state and written to coding_submissions when the interview is saved, which is where the verdict reads it.

What is saved

At the end (finalize_and_disconnect, or save_transcript_on_disconnect if the candidate leaves), collect_interview_data builds one row: both sides of the transcript with timestamps and stage, stage history and skips, how the interview ended, the track configuration and generated questions or problems, and coding submissions. It is saved to Neon Postgres through db.save_interview, which also writes the coding submissions. Feedback and the hiring verdict are generated afterwards by the web app (POST /api/feedback/verdict).

How it is tested

  • pytest (default) — unit and integration tests, including the turn loop (tests/test_interview_turn.py, tests/test_prepare_turn.py), the prompt linter, the coding flow and the problem bank's self-test.
  • pytest -m level_b tests/e2e/test_agent_audit.py — twenty scripted persona interviews across the four tracks through the text harness, asserted turn by turn (no silent turns, one question per turn, no praise adjectives, no full-name use, no stage vocabulary). Run it before changing prompts.py, interview_turn.py or interview_runtime.py.
  • tests/e2e/caption_probe.py — a live-room probe for caption timing.
