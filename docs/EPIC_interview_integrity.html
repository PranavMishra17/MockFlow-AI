Wing B — Interview Integrity (coding track)

Status, 2026-10-06: built and wired; execution still off in production. The bank, the selector, the Piston runner and the single evaluation path are all live. What remains is a production decision, not code: PISTON_ENABLED is false on the VM, so every production grade today is an AI reading of the code, labelled as such. See "Open" below.

The coding track's original weakness (audit §8): problems were LLM-invented per session, unvetted (sometimes unsolvable or ambiguous), and evaluation was LLM-only — the code was never executed, so there was no ground truth.

Done

  • Vetted problem bank (coding/problem_bank.py): nine problems — three easy, three medium, three hard — each with entrypoint, starter_code, test_cases and a reference_solution. tests/test_problem_bank.py runs every reference solution against its own tests, so the bank is provably solvable as specified.
  • Selection by level (select_problems): junior → easy, mid → medium, senior / lead / staff / principal → hard. A short pool steps down one level at a time; it never pads a senior interview with the easiest problems.
  • Wired into the agent: the coding stage selects from the bank instead of generating problems.
  • No answer key in the browser: the editor receives a client-safe view (no test_cases, no reference_solution), and the saved interview row stores the same view.
  • Editor matches the tests: Monaco is seeded with the problem's starter code, which names the entrypoint the tests call, and the signature is shown.
  • One evaluation path (interview_runtime._evaluate_code_async, called on Submit). With Piston on and a Python submission, the code runs against the hidden tests and the pass count decides correctness; the model grades approach, complexity and edge cases and writes the spoken feedback. With Piston off, or when a run fails, the result says executed: false with a not_executed_reason, a failed run is logged at WARNING, and the editor says "Not executed — reviewed by AI only".
  • The verdict sees the code: every evaluated submission is written to coding_submissions when the interview is saved, and the verdict reads the evaluator's real fields (correctness, approach quality, complexity, test result).
  • Runner: coding/piston_runner.py (hosted Piston, HTTP-mocked tests in tests/test_piston_runner.py). coding/code_runner.py (local process + timeout) is used only for the bank's own self-test in CI, never for candidate code.

Open

  1. Turn execution on in production, or decide not to. PISTON_ENABLED is off on the VM. The public emkc Piston instance is rate-limited and a third party; self-hosting Piston needs more memory than the 1 GB e2-micro has spare alongside an interview.
  2. Only Python executes. The editor accepts five languages; the bank ships Python starters and tests only. Other languages are always AI-reviewed.
  3. Rows saved before 2026-10-06 still hold the full problem dict (with the answer key) in interviews.track_config; they were not rewritten.

The execution decision (kept for reference)

The local code_runner isolates by process and timeout only — fine for the bank's trusted reference solutions, not for arbitrary candidate code.

Option What Pros Cons
A. Hosted runner (Piston) — chosen POST code to a Piston instance Real isolation off our box; multi-language External call; third-party dependency unless self-hosted
B. Subprocess + OS limits code_runner plus rlimits, no-network namespaces No external dependency Arbitrary code on the app host; isolation is hard to get right
C. Grounding without execution LLM reasons against the reference and visible tests No execution risk Not ground truth
